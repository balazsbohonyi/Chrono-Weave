2. One segment, request by request

Requests go out strictly one after another. Discovery alternates between the two ends; assessment batches serve both. The dashed line is the 180 s budget: whatever would run after it waits for the next segment.

The illustration follows the code's rules with the numbers measured in the Harriot → Halley run: each discovery request brings about 13 new pairs; assessments go out 8 at a time until the fresh pool is empty; one batch of re-asks (up to 8) follows; then the next discovery. It leaves out identity checks and the few requests the stored state cannot attribute. Page 3 prices those.

3. One task is not always one HTTP call

The 32-task cap counts tasks. Under validation failures and rate limits, one task can become several HTTP calls. They don't count against the cap but they do use the clock.
